## 方案选择

推荐：Java 负责持久化任务、投递和消费 Kafka，消费者调用现有 Python SSE 接口；前端单独订阅持久化进度。Java 保持业务协调职责，Agent 实现继续留在 Python。

备选一：Python 独立消费者直接执行 LangGraph。需要再实现跨服务完成通知、Java 侧文件与业务记录收尾，改造面更大。

备选二：在原 HTTP/SSE 连接内等待 Kafka 消费结果。不能独立满足关闭页面后任务继续、重新打开恢复进度的需求，不采用。

## 请求与执行链路

1. 前端提交应用 ID、提示词及稳定的请求幂等键。
2. Java 校验登录、应用所有权、输入长度、请求限流和待处理任务上限。在同一数据库事务中创建任务和待投递记录；提交成功后返回任务 ID。
3. 投递器读取待投递记录，将只包含任务 ID、协议版本等必要元数据的消息发送至 Kafka。收到 broker 确认后标记已投递；发送失败保留记录并退避重试。
4. 消费者根据任务 ID 从数据库读取可信输入，复核用户和应用状态，原子认领任务并调用现有 Python Agent。消息按 appId 作为 key 分区；数据库约束保证同一应用同时最多一个待处理或运行任务。
5. 消费者把阶段进度、生成文件事件和终态写入事件表。文件保存、必要构建以及 AI 聊天记录保存独立于浏览器订阅执行；全部收尾成功后才能把任务标记成功。
6. 前端按任务 ID 订阅 SSE；服务端按事件序号回放并跟进新事件。刷新后先查询应用当前或最近任务，再恢复订阅。关闭页面只停止订阅。

## 数据与接口

新增任务表、任务事件表和消息投递表，以增量 SQL 迁移创建，不改变现有数据表内容。

- 任务：taskId、appId、userId、prompt、codeGenType、idempotencyKey、状态、执行实例标识、开始/结束时间、错误码、traceId、重试关联。
- 唯一约束：同一用户和应用的幂等键唯一；同一应用的活动任务唯一，使用可空活动应用键并在终态清空。
- 事件：taskId、递增序号、事件类型、JSON 内容、创建时间；按任务和序号唯一。
- 投递记录：任务 ID、投递状态、重试次数、下次重试时间；与任务同事务建立。
- 幂等键对应的提示词不一致时拒绝请求，不能悄悄返回另一份输入的结果。
- HTTP 提交、任务查询、应用当前任务查询和 SSE 订阅均校验所有权；不能通过猜 taskId 读取他人的提示词或代码。
- 新接口采用项目现有响应封装；taskId 在前端使用字符串，避免雪花 ID 精度丢失。
- SSE 帧带事件 ID，支持游标恢复。事件重放只影响展示，不得再次触发文件保存、构建或聊天记录写入。
- 原生成入口在队列开启时也必须进入统一队列，避免绕过并发限制；兼容已有调用方的 SSE 事件协议。

## 状态与可靠性

现网兼容补充：保留 checkpoint 暂停与继续。新增 PAUSING/PAUSED 状态；暂停不释放应用任务占位，暂停完成后释放生成执行槽。继续操作使同一 taskId 再次经 Kafka 排队，并以原 Python runId 和 resume 标记恢复检查点，不能绕过队列直接执行。旧版本建立但尚未进入 MySQL 任务表的暂停任务，兼容旧状态查询，并通过受控导入后排队恢复。浏览器断开只关闭 Java 到浏览器的订阅，不中断 Java 消费者到 Python 的连接。

任务状态为 QUEUED、RUNNING、SUCCEEDED、FAILED、INTERRUPTED。已接受但 Kafka 暂时不可用的任务仍为 QUEUED，附带待投递原因。

- 数据库事务提交后才返回接受成功；投递记录避免数据库成功而 Kafka 发送失败导致任务静默丢失。
- 消息按至少一次交付处理；重复消息不能再次执行已完成任务，不能重复添加聊天记录。
- Kafka 关闭自动提交；任务终态及其事件可靠保存后再确认消费。每次拉取限制为一个任务；消费处理时限与生成总超时配套，避免长生成触发无意的分区再均衡。
- 服务正常发布先停止接收新任务执行并等待运行任务结束；恢复后继续处理排队消息。
- 进程异常中断时，核对执行归属并把无法证明完成的任务标记 INTERRUPTED，保留现有事件和错误说明。前端提供显式重试；不得把未完成任务显示成成功。
- 本期不自动重跑已开始生成但结果不确定的任务，避免旧 Python 工作仍在执行时重复改写文件或重复模型计费。重试前必须确认原执行已终止并重新取得应用执行权。
- Kafka 或网络在执行前发生的临时故障可以退避重试；输入违规、权限变化及明确的 Agent 失败保持终态，不无限重试。
- 不承诺 LLM 调用恰好一次、服务器宕机后从某个 LangGraph 节点无损续跑。浏览器断开继续执行与进程故障恢复是不同的保证。
- 限制队列容量、等待期限和事件保留量。终态结果长期由现有应用与聊天历史保存；过期事件通过任务快照解释，不能让客户端无限重连。

## 削峰与初始配置建议

以下是实施建议值，不是已验证的服务器容量：

- 初始同时执行 1 个生成任务；容量经云端测量后才能提高。
- Kafka 任务 topic 初始 1 个分区，与本期单消费者和单执行槽匹配。
- 全局最多 100 个待处理/运行任务；同应用最多 1 个活动任务。容量检查必须原子化。
- 排队最长 24 小时；超时任务明确失败，并释放活动任务占位。
- 单任务总时限 30 分钟，消费 poll 间隔上限至少 45 分钟；根据现有 Python 阶段上限和终止语义验证后落地。
- SSE 事件默认保留 7 天，定期分批清理终态任务的旧事件；活动任务事件不得清除。
- 现有鉴权、限流、Python Guardrails 和输出检查继续生效。排队负责吸收短时峰值，容量耗尽时仍明确拒绝。

## 云部署

- 原主机增加独立 Kafka 容器，使用官方 Apache Kafka 镜像和 KRaft 单节点模式；版本在实施时核对并固定，不使用 latest。
- Kafka 数据使用独立持久卷，端口仅监听回环地址或私有容器网络，advertised.listeners 与 Java 实际访问路径一致。
- 初始规划 JVM 最大堆 512 MiB，容器内存上限和日志存储预算在现场资源核查后确定。不能因加入 Kafka 导致已有应用被 OOM 杀死。
- 单节点用于当前演示规模，没有多副本故障容错保证；不额外购买服务器。
- 发布前备份相关数据库和配置；新增表保持可向后兼容，保留旧应用发布版本。回滚前停止新提交并处理活动任务，不能把新任务遗留成假运行状态。
- 新增待处理量、执行数、等待时间、执行时间、失败数及投递重试指标，接入已有监控。

## 交付与验收

交付：隔离开发分支中的前后端代码、SQL 迁移、Kafka 部署与回滚脚本、配置说明、自动化测试及云端验收记录。

必须验证：

1. 以可控生成替身同时提交至少 5 个不同应用任务，运行数始终不超过配置值，剩余任务被接受为排队，之后全部有明确终态。
2. 关闭页面后任务继续，重新打开能恢复先前进度并获得最终结果；重复连接不重复生成。
3. 同一请求幂等重试只创建一个任务；不同用户不能查询、订阅或重试他人的任务。
4. Kafka 暂停期间，容量以内的提交保留待投递记录；恢复后能够消费，重复投递不重复执行业务终态。
5. Kafka 与应用服务重启后，待处理任务可恢复；中断的执行显示 INTERRUPTED，不能静默丢失或直接报告成功。
6. Python 返回错误、缺少成功终态、Java 保存或构建失败时，任务不得标记成功。
7. 云端至少完成一次真实模型生成，验证代码文件、聊天记录、预览及页面刷新恢复。突发并发测试优先使用替身控制模型成本，必须与真实模型验收分开记录。
8. 验证 Kafka 持久化、监听范围和服务健康，记录内存与磁盘使用；验证旧应用和原有数据仍可访问。
